# 2. การวิเคราะห์ความต้องการ

- ที่มา: เกิดขึ้นหลังจากการวางแผน แปลงความต้องการทางธุรกิจให้เป็น requirements ที่มีโครงสร้าง
- จุดประสงค์: กำหนดว่าระบบต้องทำอะไรบ้างก่อนที่จะตัดสินใจออกแบบ
- ถ้าไม่มี: นักพัฒนาสร้างระบบตามสมมติฐาน ทำให้ได้ระบบที่ไม่ตอบโจทย์ปัญหาจริง

---

## ผู้มีส่วนได้ส่วนเสีย

- ที่มา: การระบุว่าใครได้รับผลกระทบหรือมีอิทธิพลต่อระบบ
- จุดประสงค์: ให้แน่ใจว่าเก็บ requirements จากคนที่ถูกต้อง
- ถ้าไม่มี: requirements สะท้อนมุมมองเดียวและพลาดความต้องการสำคัญ

- ผู้ใช้หลัก: นักวิจัย (คนเดียว, self-hosted)
- การพึ่งพาภายนอก: LLM API provider (OpenAI / Gemini)

---

## Functional Requirements

- ที่มา: มาจาก user stories — สิ่งที่ระบบต้องทำ
- จุดประสงค์: กำหนด capabilities ที่ระบบต้องมี
- ถ้าไม่มี: ไม่มีสัญญาที่ชัดเจนระหว่างสิ่งที่สร้างและสิ่งที่ต้องการ

| ID | ความต้องการ |
|----|-------------|
| FR-01 | ผู้ใช้สามารถลงทะเบียนและเข้าสู่ระบบผ่าน JWT |
| FR-02 | ผู้ใช้สามารถอัปโหลดไฟล์พร้อม metadata (title, description, category, tags) |
| FR-03 | ผู้ใช้สามารถแสดงรายการเอกสารโดยกรองตาม tag, category หรือประเภทไฟล์ |
| FR-04 | ผู้ใช้สามารถดาวน์โหลดไฟล์ตาม document ID |
| FR-05 | ผู้ใช้สามารถลบเอกสารได้ |
| FR-06 | ผู้ใช้สามารถถ่ายโอนไฟล์จาก old_server (SSH) ผ่าน our_app ไปยัง target_server (SSH หรือ S3/bucket) |
| FR-07 | ระบบรองรับ SSH เป็นทั้ง source และ destination สำหรับการถ่ายโอนไฟล์ |
| FR-08 | ระบบรองรับ S3-compatible bucket เป็น destination สำหรับการถ่ายโอน |
| FR-09 | ผู้ใช้สามารถอัปโหลดไฟล์ขนาดใหญ่ผ่าน chunked multipart POST (สูงสุด 10MB ต่อ chunk) |
| FR-10 | ระบบรวม chunks และจัดเก็บไฟล์ที่สมบูรณ์ |
| FR-11 | ผู้ใช้สามารถตรวจสอบสถานะการอัปโหลด/ถ่ายโอนผ่าน status endpoint |
| FR-12 | ผู้ใช้สามารถดูและเพิ่ม tags ให้กับเอกสาร |
| FR-13 | ระบบสามารถดึงข้อความจาก PDF และแนะนำ tags ผ่าน LLM API |
| FR-14 | ผู้ใช้สามารถยอมรับหรือปฏิเสธแต่ละ tag ที่แนะนำ |

## Non-Functional Requirements

- ที่มา: มาจากความคาดหวังด้านการดำเนินงานและคุณภาพ
- จุดประสงค์: กำหนดว่าระบบต้องทำงานได้ดีแค่ไหน ไม่ใช่แค่ทำอะไรได้
- ถ้าไม่มี: ระบบอาจทำงานถูกต้องในเชิง functional แต่ใช้งานไม่ได้จริง

| ID | ความต้องการ |
|----|-------------|
| NFR-01 | ทุก service รันผ่าน Docker Compose ด้วย `docker compose up` คำสั่งเดียว |
| NFR-02 | CI pipeline รัน lint และ pytest ทุกครั้งที่ push |
| NFR-03 | Pytest coverage >= 80% บน API layer |
| NFR-04 | ระบบรองรับไฟล์ทุกขนาดผ่าน chunked upload |
| NFR-05 | Auth ใช้ JWT |

## User Stories

- ที่มา: เขียนจากมุมมองของผู้ใช้เพื่อจับ intent และคุณค่า
- จุดประสงค์: ให้ requirements ยึดโยงกับการใช้งานจริง ไม่ใช่แค่ features ทางเทคนิค
- ถ้าไม่มี: requirements กลายเป็นนามธรรมและห่างไกลจากความต้องการจริงของผู้ใช้

```
ในฐานะนักวิจัย
ฉันต้องการอัปโหลด PDF พร้อม metadata
เพื่อที่จะสามารถค้นหาและเรียกดูได้ในภายหลัง

ในฐานะนักวิจัย
ฉันต้องการถ่ายโอนไฟล์จาก old_server (SSH) ผ่าน ResearchOS ไปยัง target_server (SSH หรือ S3)
เพื่อที่จะย้ายข้อมูลงานวิจัยระหว่าง environment โดยไม่ต้องใช้ SCP หรือ AWS CLI เอง

ในฐานะนักวิจัย
ฉันต้องการให้ระบบแนะนำ tags จากเนื้อหาเอกสาร
เพื่อที่จะไม่ต้องจัดหมวดหมู่ทุกอย่างด้วยตนเอง

ในฐานะนักวิจัย
ฉันต้องการถ่ายโอนไฟล์ขนาดใหญ่ได้อย่างน่าเชื่อถือ
เพื่อที่การอัปโหลดจะไม่ล้มเหลวเนื่องจากการขัดจังหวะของเครือข่าย
```

## ข้อจำกัด

- ที่มา: ข้อจำกัดภายนอกที่กำหนดสิ่งที่เป็นไปได้
- จุดประสงค์: กำหนดขอบเขตที่การออกแบบต้องทำงานภายใน
- ถ้าไม่มี: การออกแบบอาจเสนอวิธีแก้ปัญหาที่เป็นไปไม่ได้ในทางเทคนิคหรือทางปฏิบัติ

- นักพัฒนา 1 คน ระยะเวลา ~4–6 สัปดาห์
- ต้องรันบน Docker ทั้งหมด ไม่ต้องใช้ managed cloud services
- SSH credentials สำหรับ source/target server ต้องเก็บอย่างปลอดภัย
- S3/bucket credentials จัดการผ่าน environment variables
- LLM API calls เป็น external และมีค่าใช้จ่าย — ต้องใช้อย่างประหยัด
